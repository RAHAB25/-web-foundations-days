# Day 8 Reflection

The most difficult concept in the course was understanding how to keep data correct when many requests happen at the same time. It is easy to design an API or database schema, but a ticket sale showed me that two people can see the same seat as available and attempt to buy it together. I worked through this by separating fast, potentially stale reads from the authoritative write path. Database transactions, row locks, unique constraints, and idempotency keys each solve a different part of the problem: they prevent conflicting allocation, protect against duplicate requests, and make retries safer.

Based on feedback on my capstone, I would improve the explanation of how the architecture behaves under failure. The diagram identifies the main components, but I would add clearer sequence diagrams for payment success, payment timeout, and expired holds. I would also document measurable service-level objectives and explain how load-test results change the waiting-room admission rate. That would make the design easier for another engineer to validate instead of relying only on estimates.

Next, I want to learn more about distributed-systems observability and practical load testing. I plan to build a small prototype, generate concurrent requests against a test database, and verify that no seat can be allocated twice. I would also practise tracing a request across services and using metrics, logs, and alerts to find bottlenecks. These skills would help me move from describing a reliable design to testing whether it actually behaves reliably under pressure.
